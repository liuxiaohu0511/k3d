# 智驾数据集元数据表设计

| 项目 | 内容 |
|---|---|
| 文档版本 | V0.1（草案） |
| 编制日期 | 2026-10-12 |
| 配套文档 | 《智驾数据集存储与规划方案》 |
| 目标库 | 托管 MySQL 8.0 / PolarDB MySQL |

> 说明：字段、长度、分区数为建议值，需结合实际 clip 规模（百万级 / 千万级）和压测结果确认；DDL 为设计示例，上线前需评审。

---

## 1 设计原则

1. **只存描述与关系，不存数据本体**：传感器数据、完整 manifest、每个 clip 内各文件的哈希明细都放 OSS，库里只存路径、摘要和 clip 级哈希。
2. **版本不可变**：`released` 状态的版本，其 `version_clip`、`version_shard` 记录只允许追加元信息，不允许修改或删除，由应用层与库权限共同约束。
3. **不使用外键约束**：大表（尤其是 `version_clip`）加外键与分区冲突，且影响写入性能。引用完整性由应用层和巡检任务保证。
4. **哈希统一格式**：所有校验值带算法前缀，存为 `sha256:<64位十六进制>`，字段统一为 `VARCHAR(80)`，便于将来换算法。
5. **统一审计字段**：每张表含 `created_at`、`created_by`，可变表再加 `updated_at`、`updated_by`。
6. **软删除优先**：业务上的"删除"用状态字段表达（如 `deprecated`、`archived`），真正物理删除只由清理流程执行并写审计。

## 2 表清单与关系

| 分组 | 表 | 作用 | 预估规模 |
|---|---|---|---|
| 数据集 | `dataset` | 数据集定义 | 十到百级 |
| 数据集 | `dataset_version` | 数据集版本 | 百到千级 |
| 数据集 | `version_shard` | 版本的分片清单与哈希 | 版本数 × 数千 |
| 数据集 | `version_clip` | 版本包含哪些 clip | 版本数 × 百万级（**最大表**） |
| 数据 | `clip` | clip 索引 | 百万到千万级 |
| 数据 | `tag_dict` | 场景标签字典 | 百级 |
| 数据 | `clip_tag` | clip 与标签的关系 | clip 数 × 数个 |
| 数据 | `annotation_set` | 标注集 | 百级 |
| 数据 | `calibration` | 标定记录 | 车辆数 × 时间段 |
| 追溯 | `lineage_edge` | 血缘关系 | 随处理步骤增长 |
| 追溯 | `task_dataset_ref` | 训练任务与数据集版本引用 | 任务数 |
| 治理 | `protection` | 保护标记 | 少量 |
| 治理 | `cleanup_audit` | 清理审计 | 随清理增长 |

**关系示意（逻辑关联，无外键）**

```
dataset 1 ─── N dataset_version 1 ─── N version_shard
                    │ N
                    └── N version_clip N ─── 1 clip 1 ─── N clip_tag N ─── 1 tag_dict
                    │                         │
                    │ 引用                    └─ 通过 vehicle_id + 采集时间 关联 calibration
                    ├── annotation_set
                    └── calibration (记录在 manifest，版本级默认值)

task_dataset_ref ──→ dataset_version
lineage_edge     ──→ 任意对象（raw / clip / annotation / version / model）
protection       ──→ 任意对象（version / clip / annotation_set）
```

## 3 表结构设计

### 3.1 dataset（数据集）

```sql
CREATE TABLE dataset (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name          VARCHAR(128)  NOT NULL COMMENT '数据集唯一名，如 urban_noa_perception',
  biz_domain    VARCHAR(64)   NOT NULL COMMENT '业务方向：感知/预测/规划/仿真',
  description   VARCHAR(512)  NULL,
  owner         VARCHAR(64)   NOT NULL COMMENT '负责人',
  security_level TINYINT      NOT NULL DEFAULT 1 COMMENT '保密级别：1内部 2敏感 3严格',
  acl_group     VARCHAR(128)  NULL COMMENT '权限域/访问组',
  status        TINYINT       NOT NULL DEFAULT 1 COMMENT '1启用 0停用',
  created_at    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  created_by    VARCHAR(64)   NOT NULL,
  updated_at    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  updated_by    VARCHAR(64)   NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_name (name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='数据集定义';
```

### 3.2 dataset_version（数据集版本）

```sql
CREATE TABLE dataset_version (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  dataset_id      BIGINT UNSIGNED NOT NULL,
  version         VARCHAR(32)   NOT NULL COMMENT '如 v2.3.0',
  major           INT           NOT NULL,
  minor           INT           NOT NULL,
  patch           INT           NOT NULL,
  parent_version_id BIGINT UNSIGNED NULL COMMENT '父版本',
  status          VARCHAR(16)   NOT NULL DEFAULT 'draft' COMMENT 'draft/released/deprecated/archived',
  deprecate_reason VARCHAR(512) NULL COMMENT '作废原因，deprecated 时必填',
  clip_count      BIGINT        NOT NULL DEFAULT 0,
  total_duration_sec BIGINT     NOT NULL DEFAULT 0,
  total_size_bytes BIGINT       NOT NULL DEFAULT 0,
  split_train     BIGINT        NOT NULL DEFAULT 0,
  split_val       BIGINT        NOT NULL DEFAULT 0,
  split_test      BIGINT        NOT NULL DEFAULT 0,
  annotation_set_id BIGINT UNSIGNED NULL COMMENT '引用标注集',
  calibration_policy VARCHAR(256) NULL COMMENT '标定引用策略或标定集版本号',
  filter_rule     TEXT          NULL COMMENT '筛选规则快照（SQL/表达式），用于复现',
  tag_distribution JSON         NULL COMMENT '场景标签分布统计',
  manifest_path   VARCHAR(512)  NOT NULL COMMENT 'OSS 路径',
  manifest_hash   VARCHAR(80)   NOT NULL COMMENT 'sha256:...',
  manifest_signature VARCHAR(512) NULL COMMENT '对 manifest_hash 的签名',
  hash_algo       VARCHAR(16)   NOT NULL DEFAULT 'sha256',
  released_at     DATETIME      NULL,
  released_by     VARCHAR(64)   NULL,
  created_at      DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  created_by      VARCHAR(64)   NOT NULL,
  updated_at      DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_dataset_version (dataset_id, version),
  KEY idx_status (status),
  KEY idx_parent (parent_version_id),
  KEY idx_released_at (released_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='数据集版本';
```

要点：

- `manifest_hash` 另存一份到独立只读审计库，防止库被改后校验失效。
- `released` 后除 `status`、`deprecate_reason`、`updated_*` 外，其余字段禁止修改（应用层校验 + 触发器或权限控制）。
- `major/minor/patch` 拆开存放，方便做版本排序和"最新版本"查询。

### 3.3 version_shard（版本分片清单）

```sql
CREATE TABLE version_shard (
  version_id    BIGINT UNSIGNED NOT NULL,
  shard_no      INT           NOT NULL COMMENT '分片序号',
  shard_name    VARCHAR(64)   NOT NULL COMMENT '如 shard-000001',
  clip_count    INT           NOT NULL,
  size_bytes    BIGINT        NOT NULL,
  logical_hash  VARCHAR(80)   NOT NULL COMMENT '逻辑哈希：clip_hash 列表的哈希，进入 manifest',
  physical_hash VARCHAR(80)   NULL COMMENT '物理哈希：打包后 tar 文件字节哈希',
  cache_path    VARCHAR(512)  NULL COMMENT 'CPFS/缓存层路径',
  cache_status  VARCHAR(16)   NOT NULL DEFAULT 'none' COMMENT 'none/warming/ready/evicted',
  last_read_at  DATETIME      NULL COMMENT '最近被训练任务读取时间，用于 LRU 淘汰',
  last_verified_at DATETIME   NULL COMMENT '最近一次后台校验时间',
  verify_status VARCHAR(16)   NOT NULL DEFAULT 'unverified' COMMENT 'unverified/ok/failed',
  PRIMARY KEY (version_id, shard_no),
  KEY idx_cache_status (cache_status, last_read_at),
  KEY idx_verify (verify_status, last_verified_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='版本分片清单';
```

要点：`last_read_at` 驱动缓存 LRU 淘汰；`last_verified_at`、`verify_status` 驱动后台全量校验的调度（优先校验从未校验或很久未校验的分片）。

### 3.4 clip（片段索引）

```sql
CREATE TABLE clip (
  clip_id        VARCHAR(64)   NOT NULL COMMENT '如 clip_20260918_veh07_0032',
  vehicle_id     VARCHAR(32)   NOT NULL,
  collect_date   DATE          NOT NULL,
  city           VARCHAR(32)   NULL,
  start_ts       BIGINT        NOT NULL COMMENT '起始时间戳（毫秒）',
  end_ts         BIGINT        NOT NULL,
  duration_sec   SMALLINT      NOT NULL,
  raw_package_id VARCHAR(128)  NOT NULL COMMENT '来源原始数据包',
  raw_offset_ms  BIGINT        NULL COMMENT '在原始包中的偏移',
  data_format    VARCHAR(32)   NOT NULL COMMENT '如 mp4+pcd+parquet',
  oss_path       VARCHAR(512)  NOT NULL,
  size_bytes     BIGINT        NOT NULL,
  file_count     INT           NOT NULL,
  clip_hash      VARCHAR(80)   NOT NULL COMMENT '两层计算得到的 clip 级哈希',
  hash_algo      VARCHAR(16)   NOT NULL DEFAULT 'sha256',
  hash_detail_path VARCHAR(512) NULL COMMENT 'OSS 上各文件哈希明细清单（不入库）',
  desensitized   TINYINT       NOT NULL DEFAULT 0 COMMENT '是否已脱敏',
  qc_status      VARCHAR(16)   NOT NULL DEFAULT 'pending' COMMENT 'pending/pass/fail',
  storage_tier   VARCHAR(16)   NOT NULL DEFAULT 'standard' COMMENT 'standard/ia/archive',
  ref_count      INT           NOT NULL DEFAULT 0 COMMENT '被版本引用的计数（冗余，巡检校准）',
  last_ref_at    DATETIME      NULL COMMENT '最近一次被版本引用的时间',
  created_at     DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  created_by     VARCHAR(64)   NOT NULL,
  updated_at     DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (clip_id),
  KEY idx_vehicle_date (vehicle_id, collect_date),
  KEY idx_city_date (city, collect_date),
  KEY idx_raw_package (raw_package_id),
  KEY idx_hash (clip_hash),
  KEY idx_cleanup (ref_count, last_ref_at, storage_tier)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='clip 索引';
```

要点：

- **各文件的哈希明细不入库**。按每个 clip 约数百个文件计算，千万级 clip 会产生数十亿行，库无法承载；明细放在 OSS 旁路清单，路径记在 `hash_detail_path`。
- `ref_count` 是冗余字段，方便清理时快速筛选"引用为零"的 clip；以 `version_clip` 为准，由巡检任务定期校准。
- `idx_hash` 用于去重与对账，如果 clip 规模达到千万级且写入压力大，可评估是否改为按需查询（批量对账时再建临时表）。

### 3.5 tag_dict 与 clip_tag（场景标签）

```sql
CREATE TABLE tag_dict (
  id          INT           NOT NULL AUTO_INCREMENT,
  category    VARCHAR(32)   NOT NULL COMMENT '天气/光照/道路/事件/…',
  tag_name    VARCHAR(64)   NOT NULL COMMENT '夜间/雨天/隧道/cut-in/无保护左转',
  description VARCHAR(256)  NULL,
  status      TINYINT       NOT NULL DEFAULT 1,
  PRIMARY KEY (id),
  UNIQUE KEY uk_tag (category, tag_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='场景标签字典';

CREATE TABLE clip_tag (
  clip_id     VARCHAR(64)   NOT NULL,
  tag_id      INT           NOT NULL,
  source      VARCHAR(16)   NOT NULL COMMENT 'manual/rule/model',
  source_ver  VARCHAR(64)   NULL COMMENT '规则或模型版本',
  confidence  DECIMAL(4,3)  NULL COMMENT '置信度 0~1',
  start_ms    INT           NULL COMMENT '事件在 clip 内的起点（可选）',
  end_ms      INT           NULL,
  created_at  DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (clip_id, tag_id, source),
  KEY idx_tag_clip (tag_id, clip_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='clip 与标签关系';
```

要点：`idx_tag_clip` 支撑"按标签筛 clip"，是构建数据集时最常用的查询。主键包含 `source`，允许同一标签由人工和模型各打一份，用于对比和质检。

### 3.6 version_clip（版本与 clip 关系，最大表）

```sql
CREATE TABLE version_clip (
  version_id  BIGINT UNSIGNED NOT NULL,
  clip_id     VARCHAR(64)   NOT NULL,
  split_type  TINYINT       NOT NULL COMMENT '1train 2val 3test',
  shard_no    INT           NOT NULL COMMENT '所属分片',
  weight      FLOAT         NOT NULL DEFAULT 1.0 COMMENT '采样权重',
  PRIMARY KEY (version_id, clip_id),
  KEY idx_clip_version (clip_id, version_id),
  KEY idx_shard (version_id, shard_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
PARTITION BY HASH (version_id) PARTITIONS 64
COMMENT='版本与 clip 关系';
```

要点：

- 按 `version_id` 哈希分区，单版本查询只落一个分区；分区数按版本数与总行数调整。
- `idx_clip_version` 支撑反查"某 clip 被哪些版本引用"，是血缘追溯和清理判断的核心索引。
- 字段刻意精简以降低行宽，千万级 clip × 多版本时，行数可达数十亿，此时建议评估拆库、冷热分表，或改用 TiDB / OceanBase 一类分布式数据库。
- 完整清单同时存在于 manifest 文件中，本表是为了支持查询与反查，可从 manifest 重建。

### 3.7 annotation_set（标注集）

```sql
CREATE TABLE annotation_set (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name          VARCHAR(128)  NOT NULL COMMENT '如 ann_3d_box_v5',
  ann_type      VARCHAR(32)   NOT NULL COMMENT '3d_box/lane/seg/occupancy/trajectory',
  method        VARCHAR(16)   NOT NULL COMMENT 'manual/auto/mixed',
  producer      VARCHAR(128)  NULL COMMENT '标注团队 / 自动标注模型及版本',
  schema_ver    VARCHAR(32)   NOT NULL COMMENT '标注格式版本',
  clip_count    BIGINT        NOT NULL DEFAULT 0,
  qc_pass_rate  DECIMAL(5,2)  NULL,
  oss_path      VARCHAR(512)  NOT NULL,
  content_hash  VARCHAR(80)   NOT NULL COMMENT '标注集整体哈希（按 clip_id 排序拼接）',
  hash_detail_path VARCHAR(512) NULL,
  status        VARCHAR(16)   NOT NULL DEFAULT 'draft' COMMENT 'draft/released/deprecated',
  parent_id     BIGINT UNSIGNED NULL COMMENT '上一版标注集',
  created_at    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  created_by    VARCHAR(64)   NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_name (name),
  KEY idx_type_status (ann_type, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='标注集';
```

### 3.8 calibration（标定）

```sql
CREATE TABLE calibration (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  vehicle_id    VARCHAR(32)   NOT NULL,
  calib_version VARCHAR(32)   NOT NULL COMMENT '如 calib_v3',
  valid_from    DATETIME      NOT NULL,
  valid_to      DATETIME      NULL COMMENT 'NULL 表示当前仍有效',
  sensor_scope  VARCHAR(128)  NULL COMMENT '覆盖传感器范围',
  quality_score DECIMAL(5,2)  NULL,
  oss_path      VARCHAR(512)  NOT NULL,
  file_hash     VARCHAR(80)   NOT NULL,
  status        VARCHAR(16)   NOT NULL DEFAULT 'valid' COMMENT 'valid/invalid',
  invalid_reason VARCHAR(512) NULL COMMENT '标定被判错时记录原因，用于血缘反查',
  created_at    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  created_by    VARCHAR(64)   NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_vehicle_version (vehicle_id, calib_version),
  KEY idx_vehicle_time (vehicle_id, valid_from, valid_to)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='标定记录';
```

要点：clip 与标定通过 `vehicle_id` + 采集时间落入 `valid_from ~ valid_to` 关联。发现标定错误时，将该记录置为 `invalid` 并填写原因，再通过 clip 的车辆和时间范围反查受影响的版本。

### 3.9 lineage_edge（血缘）

```sql
CREATE TABLE lineage_edge (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  up_type        VARCHAR(16)   NOT NULL COMMENT 'raw/clip/annotation/version/model',
  up_id          VARCHAR(128)  NOT NULL,
  down_type      VARCHAR(16)   NOT NULL,
  down_id        VARCHAR(128)  NOT NULL,
  process_name   VARCHAR(64)   NOT NULL COMMENT '脱敏/切片/标注/筛选/训练',
  process_version VARCHAR(64)  NULL COMMENT '处理程序版本，如 脱敏程序 v1.4',
  params         JSON          NULL COMMENT '处理参数',
  run_id         VARCHAR(128)  NULL COMMENT '流水线或任务运行 ID',
  executed_at    DATETIME      NOT NULL,
  executed_by    VARCHAR(64)   NULL,
  PRIMARY KEY (id),
  KEY idx_up (up_type, up_id),
  KEY idx_down (down_type, down_id),
  KEY idx_run (run_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='血缘关系（边表）';
```

要点：

- 采用"边表"结构，每条记录表示"上游对象经某处理产生下游对象"，可以统一表达 `raw → clip → annotation → version → model` 的链路。
- **粒度控制**：clip 级别的边量极大，建议 raw → clip 这一层按"原始包 → 一批 clip"记录批次关系（`down_id` 填批次号），不逐 clip 落边。
- 向上追溯用 `idx_down`，向下影响分析用 `idx_up`，多层链路用递归查询（MySQL 8 的 `WITH RECURSIVE`）。

### 3.10 task_dataset_ref（任务与数据集引用）

```sql
CREATE TABLE task_dataset_ref (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  task_id         VARCHAR(64)   NOT NULL COMMENT '如 train_8821',
  task_type       VARCHAR(16)   NOT NULL COMMENT 'train/eval/replay',
  attempt_no      INT           NOT NULL DEFAULT 1 COMMENT '第几次尝试（重试/续跑）',
  version_id      BIGINT UNSIGNED NOT NULL,
  manifest_hash   VARCHAR(80)   NOT NULL COMMENT '启动时实际校验到的哈希',
  verify_result   VARCHAR(16)   NOT NULL COMMENT 'pass/fail',
  verify_detail   JSON          NULL COMMENT '各校验项结果、抽检比例、随机种子、失败分片',
  verify_cost_ms  INT           NULL,
  resume_from     VARCHAR(256)  NULL COMMENT '续跑起点（分片/偏移），首次启动为空',
  model_artifact_id VARCHAR(128) NULL COMMENT '产出模型 ID',
  started_at      DATETIME      NOT NULL,
  finished_at     DATETIME      NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_task_attempt (task_id, attempt_no),
  KEY idx_version (version_id, started_at),
  KEY idx_model (model_artifact_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='任务引用的数据集版本';
```

要点：`attempt_no` 记录重试与续跑，每次尝试都做版本与哈希校验并留痕；`verify_detail` 记录随机种子和失败分片，便于复现校验问题。

### 3.11 protection（保护标记）

```sql
CREATE TABLE protection (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  target_type  VARCHAR(16)   NOT NULL COMMENT 'version/clip/annotation_set/calibration',
  target_id    VARCHAR(128)  NOT NULL,
  reason_type  VARCHAR(32)   NOT NULL COMMENT 'release/baseline/compliance/incident',
  reason       VARCHAR(512)  NOT NULL,
  protected_until DATE       NULL COMMENT 'NULL 表示长期保护',
  created_at   DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  created_by   VARCHAR(64)   NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_target (target_type, target_id, reason_type),
  KEY idx_until (protected_until)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='保护标记，清理程序必须跳过';
```

要点：清理前先查本表。模型发布、验收基线、合规留存、事故复盘等场景由对应流程自动写入，避免依赖人工记忆。

### 3.12 cleanup_audit（清理审计）

```sql
CREATE TABLE cleanup_audit (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  target_type  VARCHAR(16)   NOT NULL,
  target_id    VARCHAR(128)  NOT NULL,
  action       VARCHAR(16)   NOT NULL COMMENT 'mark/freeze/archive/delete/restore',
  rule_id      VARCHAR(32)   NOT NULL COMMENT '触发规则，如 R-07',
  rule_snapshot VARCHAR(512) NULL COMMENT '规则内容快照',
  size_bytes   BIGINT        NULL COMMENT '释放或涉及的容量',
  recoverable  TINYINT       NOT NULL DEFAULT 0,
  operator     VARCHAR(64)   NOT NULL COMMENT '系统或人员',
  created_at   DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_target (target_type, target_id),
  KEY idx_time (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='清理审计，只追加';
```

## 4 状态机

**数据集版本**

```
draft ──发布校验通过──▶ released ──发现问题/被替代──▶ deprecated ──超保留期、无依赖──▶ archived
  │                                                         
  └──长期无引用──▶ （清理流程）删除 manifest 与派生缓存
```

约束：

- 只有 `released` 才允许被正式训练任务引用。
- `deprecated` 必须填写 `deprecate_reason`，且仍允许被已有模型追溯。
- `released → draft` 不允许回退。

**clip 存储层级**：`standard → ia → archive`，由清理流程按 `ref_count`、`last_ref_at` 推动，写 `cleanup_audit`。

**缓存分片**：`none → warming → ready → evicted`，由预热任务和 LRU 淘汰推动。

## 5 典型查询

**5.1 某版本包含哪些 clip（按分片）**

```sql
SELECT clip_id, split_type, weight
FROM version_clip
WHERE version_id = ? AND shard_no = ?;
```

**5.2 某 clip 被哪些版本引用**

```sql
SELECT v.version, v.status, d.name
FROM version_clip vc
JOIN dataset_version v ON v.id = vc.version_id
JOIN dataset d ON d.id = v.dataset_id
WHERE vc.clip_id = ?;
```

**5.3 某模型是用哪个版本训练的**

```sql
SELECT t.task_id, t.attempt_no, d.name, v.version, t.manifest_hash, t.verify_result
FROM task_dataset_ref t
JOIN dataset_version v ON v.id = t.version_id
JOIN dataset d ON d.id = v.dataset_id
WHERE t.model_artifact_id = ?;
```

**5.4 标定错误的影响范围（以 veh07 的 9 月 1 日至 5 日为例）**

```sql
-- 受影响 clip
SELECT clip_id FROM clip
WHERE vehicle_id = 'veh07'
  AND collect_date BETWEEN '2026-09-01' AND '2026-09-05';

-- 受影响版本、任务、模型（先将上面结果物化为临时表 tmp_bad_clip）
SELECT DISTINCT v.version, t.task_id, t.model_artifact_id
FROM tmp_bad_clip b
JOIN version_clip vc ON vc.clip_id = b.clip_id
JOIN dataset_version v ON v.id = vc.version_id
LEFT JOIN task_dataset_ref t ON t.version_id = v.id;
```

**5.5 按标签与条件构建新版本的候选 clip**

```sql
SELECT c.clip_id
FROM clip c
JOIN clip_tag t1 ON t1.clip_id = c.clip_id AND t1.tag_id = ?   -- 夜间
JOIN clip_tag t2 ON t2.clip_id = c.clip_id AND t2.tag_id = ?   -- cut-in
WHERE c.qc_status = 'pass' AND c.desensitized = 1;
```

**5.6 清理候选：无任何版本引用、超过保留期、未受保护的 clip**

```sql
SELECT c.clip_id, c.size_bytes
FROM clip c
LEFT JOIN protection p
  ON p.target_type = 'clip' AND p.target_id = c.clip_id
WHERE c.ref_count = 0
  AND c.last_ref_at < NOW() - INTERVAL 90 DAY
  AND c.storage_tier = 'standard'
  AND p.id IS NULL;
```

**5.7 缓存淘汰候选：近 14 天无读取的就绪分片**

```sql
SELECT version_id, shard_no, cache_path
FROM version_shard
WHERE cache_status = 'ready'
  AND last_read_at < NOW() - INTERVAL 14 DAY;
```

## 6 容量与性能规划

| 项 | 建议 |
|---|---|
| `clip` 表 | 千万级以内单表可承载；超过后按 `collect_date` 做范围分区，便于冷数据下沉 |
| `version_clip` 表 | 按 `version_id` 哈希分区；行数达到数十亿时考虑分库或换分布式数据库 |
| 批量写入 | 入库流水线批量插入（每批数千行），关闭逐行事务；构建版本时先写分片再批量写关系 |
| 大查询 | 反查、对账类查询走只读副本，避免影响在线校验写入 |
| 冗余字段 | `ref_count`、`clip_count` 等冗余字段定期用巡检任务校准，以关系表为准 |
| 大对象 | 完整 manifest、clip 内文件哈希明细一律放 OSS，库内只存路径与摘要 |
| 归档 | 已 `archived` 的版本，其 `version_clip` 可导出为文件并从在线库迁走，需要时再导入 |

## 7 一致性与巡检

| 巡检项 | 做法 | 频率 |
|---|---|---|
| 库与 OSS 对账 | 对比 OSS 对象列表与 `clip.oss_path`，发现孤儿对象与缺失对象 | 每日 / 每周 |
| 引用计数校准 | 用 `version_clip` 重算 `clip.ref_count` 并修正 | 每日 |
| manifest 一致性 | 抽查 `dataset_version.manifest_hash` 与 OSS 上 manifest 重算值、独立审计库中的值三方比对 | 每周 |
| 统计字段校准 | 对比 `dataset_version.clip_count` 与 `version_clip` 实际行数 | 每次发布与每周 |
| 分片校验 | 按 `last_verified_at` 优先级调度后台全量校验，结果写回 `verify_status` | 持续 |
| 状态合法性 | 检查是否有 `released` 版本被改动，是否有 `draft` 版本被正式任务引用 | 每日 |

## 8 权限与安全

1. **角色分离**：入库流水线账号有写 `clip`、`clip_tag` 的权限；版本发布账号有写 `dataset_version`、`version_*` 的权限；训练任务账号只有读，外加写 `task_dataset_ref`；清理程序账号只能更新 `storage_tier`、`ref_count` 及写 `cleanup_audit`。
2. **released 版本防篡改**：除状态字段外，禁止 UPDATE；库侧用触发器或权限拦截，应用层二次校验。
3. **审计库独立**：`manifest_hash` 副本与签名放在独立只读库或 OSS 保留策略位置，普通账号无写权限。
4. **敏感字段**：涉及位置、车辆标识等敏感信息的字段，按数据集 `security_level` 控制可见范围，必要时脱敏展示。

## 9 待确认事项

1. clip 总量与版本数量，决定 `version_clip` 是否分库分表，或改用分布式数据库。
2. clip 与标定的关联方式：按车辆与时间区间自动关联，还是在 manifest 中显式记录每个 clip 使用的标定版本。
3. 标注是否按 clip 记录版本（同一版本内混用多个标注集），如需要，应新增 `version_annotation` 关联表。
4. 血缘记录的粒度（批次级还是 clip 级），以及是否对接已有的数据治理或流水线平台。
5. 各类保留期与保护规则，需与合规要求对齐后固化到 `protection` 和清理规则里。
