| 方案 | 适用场景 | 优点 | 风险 / 代价 |
|---|---|---|---|

| MLMD / MLflow 一类 | 实验、模型、产物血缘管理 | 生态现成 | 偏实验管理，不负责调度级的重试与状态机，多数是补充而不是替代 |

**我的默认建议**：以托管 MySQL / PolarDB 作为任务状态与 CheckPoint 元数据的事实源，Redis 负责去重和限流，CheckPoint 本体放 OSS / NAS。CRD 只保留最小运行态，不承载历史数据。选型评审时可重点对比写入 QPS、故障切换时间（RTO / RPO）、与现有作业框架的改造量，这些也对应文档里 4.4 的验收指标。

## 第 2 轮

**用户**

数据集能用mldb的方案存储和规划吗？

**Claude**

**能，但要分清"存元数据"和"存数据本体"。** 我仍按上一轮的理解，把 mldb 当作元数据库方案来回答。如果你指的是 MLDB.ai 本身，或公司内部某个系统，请告诉我，结论会不同。

**1. 数据集本体：不适合放进 mldb 一类的数据库**

训练数据集通常是大量文件或大对象（图片、文本分片、Parquet、TFRecord 等），体量从 GB 到 TB 甚至 PB。数据库不适合承载这类数据，写入和读取吞吐也撑不住训练的并发读取。本体建议这样放：

| 数据类型 | 推荐存储 | 说明 |
|---|---|---|
| 冷数据 / 原始数据 / 归档 | OSS | 成本低，容量几乎无上限 |
| 训练热数据 | CPFS / NAS，或 OSS + 本地缓存加速（如 Fluid） | 提供高吞吐、多节点并发读 |
| 节点本地临时数据 | 本地盘（限额管控） | 仅作缓存，需配 ephemeral-storage 限额 |

**2. 数据集元数据：适合放进 mldb 方案**

可以存放：数据集名称、版本号、存储路径、schema、样本数量、大小、校验值（checksum）、血缘（来源和处理流程）、权限、状态、以及"哪些任务用了哪个版本"的引用关系。

数据集版本管理和任务的重试、断点续跑是联动的。如果任务中断后重跑，数据集版本变了，结果会不可复现。所以任务启动时应记录数据集版本号，重试时必须读同一版本。

**3. 规划时要和文档里的几个专项联动**

- **磁盘高占用（4.2）**：数据集不能无限制拉到节点本地盘，要设置缓存上限和淘汰策略，任务结束后自动清理。
- **镜像带宽（4.5）**：数据集不要打进镜像，否则镜像过大会加剧带宽打满。数据和镜像要分离。
- **断点续跑（4.4）**：数据读取位置（偏移量、已处理分片）可以随 CheckPoint 一起记录，中断后从断点继续读。
- **算力可用率**：数据加载慢会让 GPU 空等，影响算力利用率。规划时要评估读取吞吐是否跟得上卡数。

**4. 规划建议（可落地的最小方案）**

1. 元数据库用托管 MySQL / PolarDB 存数据集版本、路径、血缘和引用关系。
2. 数据本体放 OSS，热数据通过 CPFS 或缓存层加速。
3. 建立数据集版本规范：版本不可变，新增数据一律生成新版本。
4. 训练任务启动时强制校验数据集版本和 checksum。
5. 定期清理无引用的旧版本和缓存，并纳入巡检。

这部分详细说下，每一步存储的内容是什么。以智能驾驶场景为例说明

**Claude**

下面以"城区 NOA 感知模型训练"为例，按五步逐一说明各层存什么。示例中的字段、路径和数值是为说明而假设的，需按你们的实际数据结构调整。

**先约定场景里的数据**

- **原始采集数据**：车端录制的数据包（MCAP / rosbag / 自定义 record），含 7–11 路摄像头、激光雷达点云、毫米波雷达、IMU、GNSS、CAN 信号，单车单日可达几百 GB。
- **Clip（片段）**：从原始数据切出的 15–30 秒训练单元，是数据集的基本管理粒度。
- **标注**：2D / 3D 框、车道线、语义分割、Occupancy、轨迹真值等，由标注平台或自动标注产出，会多次迭代。
- **标定参数**：相机内外参、雷达外参、时间同步偏移，不同车辆、不同时间各不相同，标错会直接毁掉训练效果。
- **场景标签**：夜间、雨天、隧道、施工区、cut-in、无保护左转等，是筛选数据集的依据。

**一个关键设计：数据集版本 = 清单（manifest），不复制数据本体。** 数据集版本只记录"选了哪些 clip、用哪一版标注、哪一版标定"，本体始终在 OSS 里。这样同一批数据可以被几十个版本引用，不会重复占用存储。

#### 第 1 步：元数据库（MySQL / PolarDB）存什么

元数据库只存"描述和关系"，不存任何传感器数据。

| 表 | 存储内容 | 示例 |
|---|---|---|
| dataset（数据集） | 数据集名称、业务方向、负责人、权限域 | `urban_noa_perception`，负责人，保密级别 |
| dataset_version（数据集版本） | 版本号、状态（draft / released / deprecated）、创建时间、clip 总数、总时长、总大小、**manifest 路径、manifest 哈希**、筛选规则快照、父版本 | `v2.3.0`，clip 数 120 万，manifest 哈希 `sha256:…`，父版本 `v2.2.0` |
| clip（片段索引） | clip_id、来源车辆 / 采集日期 / 城市、起止时间、OSS 路径、原始数据包 ID、数据格式、大小、**对象校验值** | `clip_20260918_veh07_0032`，路径 `oss://…/clips/…` |
| clip_tag（场景标签） | clip_id 与标签的多对多关系，标签来源（人工 / 规则 / 模型）和置信度 | 夜间、雨天、cut-in |
| version_clip（版本与 clip 关系） | version_id、clip_id、划分（train / val / test）、采样权重 | `v2.3.0` 含该 clip，归入 train，权重 1.0 |
| annotation_set（标注集） | 标注版本号、标注类型、标注方式（人工 / 自动）、质检通过率、标注文件路径与校验值 | `ann_3d_box_v5`，质检通过率 98.7% |
| calibration（标定） | 车辆 ID、生效时间段、标定文件路径、校验值、标定质量评分 | `veh07`，2026-09-01 至 2026-09-30 |
| lineage（血缘） | 上游到下游的处理关系：采集 → 脱敏 → 切片 → 标注 → 筛选 → 数据集，记录处理程序版本、参数、执行时间、执行人 | `脱敏程序 v1.4` 处理了某批原始包 |
| task_dataset_ref（引用关系） | 任务 ID、使用的数据集版本、启动时校验结果、模型产物 ID | 训练任务 `train_8821` 使用 `v2.3.0`，校验通过 |

**常用查询**：某数据集版本包含哪些 clip；某 clip 被哪些版本引用；某模型是用哪个版本训练出来的（可复现与问题追溯）；某批数据脱敏出过问题，影响哪些版本和模型（血缘反查）。

**注意**：百万级 clip 乘以多版本，`version_clip` 表会很大，需按 version_id 分区或分表。manifest 完整内容放 OSS，库里只存摘要和哈希，避免把大对象塞进数据库。

#### 第 2 步：数据本体（OSS + CPFS / 缓存）存什么

**OSS 目录示意**

```
oss://ad-data/
├── raw/        原始数据包（按采集日期 / 车辆）
│   └── 2026-09-18/veh07/xxx.mcap
├── clips/      切片后的训练单元（按 clip_id）
│   └── clip_xxx/{cam_*.jpg|video, lidar.pcd, can.parquet, meta.json}
├── annotations/    标注结果（独立版本目录）
│   └── ann_3d_box_v5/clip_xxx.json
├── calibration/    标定文件
├── manifests/      数据集清单（不可变）
│   └── urban_noa_perception/v2.3.0.manifest
└── archive/        冷数据归档
```

要点：标注与 clip 分目录存放，因为标注会反复改而图像不变，分开后改标注只生成新标注版本，不用动 clip 本体。

**分层存储策略**

| 层级 | 存储 | 放什么 | 说明 |
|---|---|---|---|
| 冷 | OSS 归档 / 低频 | 原始数据包、过期版本涉及的 clip | 成本最低，需要时回迁 |
| 温 | OSS 标准 | 全量 clip、标注、manifest | 数据事实源 |
| 热 | CPFS，或 OSS + Fluid 缓存 | 当前训练版本涉及的 clip | 提供高吞吐、多节点并发读，避免 GPU 等数据 |
| 节点本地 | 本地盘（限额） | 小文件打包后的缓存块 | 必须配合 4.2 的磁盘限额与自动清理 |

**智驾场景的两个特殊点**

- **小文件问题**：clip 内有大量图片和点云帧，直接按文件读取会拖垮 OSS 和 CPFS 的元数据性能。建议训练前把 clip 打包成较大的分片文件（如 WebDataset / TFRecord / 自定义块格式），读取时顺序读。
- **数据与镜像分离**：数据集绝不打进镜像，通过挂载或缓存层访问，否则会加剧 4.5 的镜像带宽问题。

#### 第 3 步：数据集版本规范存什么、规定什么

**版本号规则（建议）**

- **主版本**：筛选规则或划分策略变化（比如新增"夜间数据占比 ≥ 20%"要求）
- **次版本**：新增数据（新采集一批 clip）
- **修订版本**：只更新标注或修正标签

**manifest 文件内容（一个版本一个，生成后只读）**

- 版本号、父版本、创建人、创建时间
- 筛选规则快照（SQL 或规则表达式，用于复现）
- clip 列表：clip_id、OSS 路径、对象校验值、划分（train / val / test）
- 引用的标注集版本、标定版本
- 统计摘要：各场景标签分布、总时长、各城市占比
- manifest 自身哈希

**不可变如何落地**

1. manifest 写入 OSS 后开启保留策略（WORM）或严格权限，禁止覆盖。
2. clip 和标注对象开启 OSS 版本控制，禁止原地覆写；修改一律新增对象。
3. 状态流转：`draft → released → deprecated`；只有 `released` 才允许被正式训练任务引用。
4. 修复数据错误（比如发现某批 clip 标定错误）：不修改旧版本，生成新版本，并把旧版本标记为 `deprecated` 并注明原因，血缘能反查受影响的模型。

#### 第 4 步：训练启动时校验，校验什么

**校验内容与存储位置**

| 校验项 | 对比对象 | 失败处理 |
|---|---|---|
| 版本状态 | 库中状态必须为 released | 拒绝启动，提示改用有效版本 |
| manifest 完整性 | 重新计算 manifest 哈希，与库中记录比对 | 拒绝启动，触发告警 |
| 标注 / 标定版本 | manifest 引用的版本与实际文件校验值 | 拒绝启动 |
| 数据对象抽检 | 随机抽取一定比例 clip，对比对象校验值 | 超过失败阈值则拒绝启动 |
| 可读性与缓存就绪 | 热数据是否已预热到 CPFS / 缓存 | 未就绪则等待或降级读 OSS |

**为什么是抽检而非全量**：百万级 clip 全量校验耗时过长，会拖慢启动并占用带宽。建议用"manifest 哈希全量校验 + 对象抽检 + 后台全量校验任务"的组合；manifest 内部可以按分片做哈希树，出问题时快速定位到具体分片。

**启动后写入库的内容（`task_dataset_ref`）**：任务 ID、数据集版本、manifest 哈希、校验结果与耗时、启动时间、关联的模型产物 ID。

**与 4.4 联动**：重试或断点续跑时，任务必须读取同一个数据集版本；CheckPoint 里记录版本号和已消费的分片 / 偏移量，续跑前再校验一次版本一致，避免续跑时数据悄悄变了。

#### 第 5 步：清理与巡检，清理什么、依据什么

**清理对象与判断依据**

| 对象 | 判断依据 | 动作 |
|---|---|---|
| 无引用的 draft 版本 | 超过 N 天未被任何任务引用 | 标记后删除 manifest 与派生缓存 |
| 过期的 deprecated 版本 | 超过保留期且无模型依赖 | 归档或删除，不删 clip 本体（可能仍被其他版本引用） |
| 无任何版本引用的 clip | 引用计数为 0，且超过保留期 | 转冷存储，再超期后删除 |
| CPFS / 缓存中的热数据 | 对应版本近 N 天无任务读取 | 按 LRU 淘汰，保留 OSS 事实源 |
| 节点本地缓存 | 任务结束或超出限额 | 自动清理（对应 4.2） |
| 孤儿对象 | OSS 中存在但库里无索引 | 巡检发现后人工确认再清理 |

**必须保护、不可自动清理的对象**：量产交付版本涉及的数据与模型依赖的数据、验收基线、安全或法规要求留存的数据（智驾对事故复盘和合规追溯有要求）、被已发布模型引用的版本。这些在库里打"保护"标记，清理程序跳过。

**清理流程**：标记 → 冻结期（期间可恢复）→ 归档 → 真正删除，每一步写审计记录（谁、何时、依据什么规则）。

**巡检项（对应第 5 章监控）**：元数据与 OSS 对象一致性、孤儿对象数量、缓存命中率、CPFS 容量水位、各版本引用计数、校验失败次数、冷热数据占比。

#### 小结：每层的职责边界

| 层 | 存什么 | 不存什么 |
|---|---|---|
| MySQL / PolarDB | 版本、索引、血缘、引用、校验值 | 任何传感器数据、完整 manifest |
| OSS | 原始包、clip、标注、标定、manifest（事实源） | 临时缓存 |
| CPFS / 缓存 | 当前训练版本的热数据副本 | 事实源数据 |
| 节点本地盘 | 打包后的短期缓存块 | 长期数据 |

有两个前提需要你确认，会影响具体方案：一是 clip 总量和单版本规模（百万级还是千万级），决定元数据库要不要分库分表；二是是否涉及数据合规要求，比如脱敏、数据不出境，这会影响 OSS 地域和权限设计。

各个步骤的校验值 是怎么加工的、

**Claude**

校验值本质上都是**对"内容"算出的一个固定长度的指纹**：内容变一个字节，指纹就完全不同。下面按前面各步出现的校验值，说明怎么算、在哪算、存在哪。示例的哈希值都是虚构的。

#### 先讲通用原理

- **算法**：用 SHA-256（需要更快时可用 xxHash / CRC32C 做快速校验，但防篡改场景用 SHA-256）。
- **输入**：文件的原始字节流，与文件名、路径、修改时间无关。
- **输出**：64 位十六进制字符串，如 `sha256:9f3a…c1`。
- **特点**：同样的内容永远得到同样的值，改动任意一位，结果完全不同。

形象理解：给每份数据按个"指纹"，之后比对指纹就知道数据有没有被动过。

#### 1. clip 对象校验值（第 1 步 clip 表里的那一列）

**一个 clip 有几十个文件，指纹是分两层算的：**

```
clip_20260918_veh07_0032/
  cam_front.mp4   → sha256 = a1…
  cam_left.mp4    → sha256 = b2…
  lidar_000.pcd   → sha256 = c3…
  ...
  can.parquet     → sha256 = d4…
  meta.json       → sha256 = e5…
```

然后把这些文件指纹按**文件名排序后拼接**，再算一次哈希，得到 clip 级指纹：

```
clip_hash = sha256( "cam_front.mp4:a1…\ncam_left.mp4:b2…\n…" )
         = sha256:9f3a…c1
```

**关键细节**

- 必须**固定排序**，否则同样内容因读取顺序不同会算出不同结果。
- 文件名要参与计算，避免两个文件内容互换却不被发现。
- 大文件用**流式分块计算**（比如每次读 8 MB），不用一次读入内存。

**在哪算、何时算**：数据写入 OSS 的入库流水线里算（切片完成后），算完把 clip_hash 和各文件哈希写入元数据库，同时作为对象元数据或旁路清单文件保存。
也可以利用 OSS 自带的 ETag / CRC64 做上传完整性校验，但 ETag 不一定等于内容哈希（分片上传时是分片摘要的组合值），所以**业务侧仍应自算 SHA-256 作为事实指纹**。

#### 2. 标注集、标定文件校验值（第 1、4 步）

- **标定文件**（如 calib_v3.yaml）是小文本文件，直接对文件字节算 SHA-256。
- **标注集**（如 ann_3d_box_v5）有成千上万个 JSON，做法与 clip 相同：每个标注文件算哈希，再按 clip_id 排序后拼接，得到标注集整体哈希。

一个坑：JSON 的**字段顺序、空格、换行**不同会导致哈希不同，但内容语义相同。解决办法是写入时用**规范化序列化**（字段排序、固定缩进、统一换行符与编码 UTF-8）后再算，保证同样的内容永远得到同样的字节。

#### 3. manifest 哈希（第 3 步，最关键的一个）

manifest 的校验分三层，类似**哈希树**：

```
第一层：每个 clip 的 clip_hash（来自第 1 项）
          ↓
第二层：每个 shard（分片，如 800 个 clip）的 shard_hash
        shard_hash = sha256( 该分片内 clip_id 排序后，拼接 "clip_id:clip_hash" )
          ↓
第三层：manifest_hash
        manifest_hash = sha256( 版本号 + 父版本 + 筛选规则 + 标注集哈希
                              + 标定哈希 + 所有 shard_hash 按序拼接 )
```

示意：

```
shard-000001: sha256:1a2b…   （800 个 clip）
shard-000002: sha256:3c4d…
...
manifest_hash: sha256:b71e…44
```

**为什么分层**：

- 百万 clip 全量重算太慢，分层后可以**只校验顶层哈希**就确认整体没变。
- 顶层不一致时，逐层往下比，**快速定位到是哪个分片、哪个 clip 出了问题**。
- 新增一批数据生成新版本时，**没变的分片哈希可以复用**，不用重算。

**注意**：manifest_hash 计算时，`manifest_hash` 字段本身要排除在外，否则自己包含自己，无法计算。

#### 4. 训练数据分片（shard）的校验值（第 2、4 步）

训练前把 clip 打包成 `shard-000001.tar`，这里有两种哈希，别混淆：

| 哈希 | 算的对象 | 用途 |
|---|---|---|
| 逻辑哈希（shard_hash） | 分片内 clip 的 clip_hash 列表 | 证明"内容是哪些 clip"，进入 manifest |
| 物理哈希（文件哈希） | 打包后的 tar 文件字节 | 证明"这个缓存文件传输和存储没损坏" |

原因：同样的 clip，不同打包工具或顺序，tar 文件字节可能不同，所以逻辑哈希用来判定"数据是否一致"，物理哈希用来判定"缓存文件是否完好"。打包时两个都算，物理哈希随分片存在缓存层的清单里。

#### 5. 启动校验时是怎么用的（第 4 步）

校验就是**重新算一遍，再与库里记录的值比对**：

| 校验项 | 重新计算什么 | 比对对象 |
|---|---|---|
| manifest 完整性 | 读取 manifest 文件，按规则重算 manifest_hash | 库里 dataset_version 的哈希 |
| 标注 / 标定 | 对文件字节重算 | manifest 内记录的值 |
| 数据抽检 | 随机抽 1% 的分片，重算物理哈希（或解包重算 clip_hash） | 清单里的值 |
| 缓存可读性 | 读取分片头部并校验大小 | 清单里的大小 |

**抽检的实现要点**：

- 抽样要用**随机种子**并记录进日志，出问题时可复现。
- 重点抽**最近改动过的分片**和**上次校验失败过的分片**，比纯随机更有效。
- 后台另起一个全量校验任务，慢慢把所有分片查完，结果写回库里。

#### 6. 清理巡检时的用法（第 5 步）

- **孤儿对象识别**：对 OSS 对象列表与库里 clip_hash 做对账，找出"库里没有记录的对象"。
- **静默损坏检测**（存储介质悄悄坏位）：定期随机重算冷数据哈希，与库里值比对，发现不一致就从副本恢复并告警。
- **去重**：相同 SHA-256 的对象视为同一份内容，可合并存储，节省空间。

#### 7. 存放位置与安全要点

| 校验值 | 存放位置 |
|---|---|
| 文件 / clip 哈希 | 元数据库 clip 表，同时写在 OSS 对象元数据或旁路清单中 |
| shard 哈希 | manifest 文件内 + 缓存层清单 |
| manifest_hash | 元数据库 dataset_version 表，并**另存一份到独立的只读位置**（如审计库） |

**最后一条很重要**：如果哈希与数据存在同一处，有权限的人可以同时改数据和哈希，校验就失去意义。所以 manifest_hash 建议**独立存放并限制写权限**，必要时对其做签名（用密钥对 manifest_hash 签名，校验时先验签），这样即使库被改也能发现。

#### 实施时的几个工程提示

1. **计算开销**：百万 clip 的 TB 级数据重算 SHA-256 需要大量 IO 与 CPU，所以哈希在**入库时算一次**，之后只做抽检和后台校验。
2. **并行化**：入库流水线按文件并行计算哈希，多个 worker 同时处理，再由汇总步骤按固定顺序拼接。
3. **算法版本**：哈希值前缀写明算法（如 `sha256:`），以后换算法时不会混淆。
4. **规范化是前提**：凡是文本类数据（JSON、YAML、CSV），一定先规范化再哈希，否则会出现"内容没变但哈希变了"的误报。

- 数据集：`dataset`、`dataset_version`、`version_shard`、`version_clip`
- 数据：`clip`、`tag_dict`、`clip_tag`、`annotation_set`、`calibration`
- 追溯：`lineage_edge`（血缘）、`task_dataset_ref`（任务引用）
- 治理：`protection`（保护标记）、`cleanup_audit`（清理审计）

**配套内容**：
- 版本和缓存分片的状态机
- 7 个典型查询，如标定错误的影响范围、清理候选、缓存淘汰候选
- 容量规划、库与对象存储的对账巡检、权限设计

**设计取舍**（文档里有说明）：
- 不加外键：大表加外键与分区冲突，引用完整性靠应用层和巡检保证。
- clip 内各文件的哈希明细不入库：数量会到数十亿行，明细放 OSS，库里只存 clip 级哈希和明细路径。
- `version_clip` 是最大的表，按 `version_id` 哈希分区；规模到数十亿行时要考虑分库或换分布式数据库。

文末列了 5 个待确认事项。其中 clip 规模和"标定如何与 clip 关联"会直接影响表结构，建议先确认。字段长度、分区数都是建议值，需结合你们的实际规模调整。

## 第 10 轮

**用户**

很多平台都在使用数据湖的思想在管理元数据，是否有其必要和合理性？

**Claude**

**合理，但不是必须，而且不该整体替换。** 更实际的做法是"控制面用关系库，大体量分析面用数据湖表格式"的混合方案，是否上湖取决于规模和查询模式。

#### 数据湖思想对元数据的价值

这里的"数据湖"主要指 Iceberg、Delta、Hudi、Paimon 这类湖仓表格式，数据落在 OSS 上，由 Spark、Flink、Trino 等引擎读写。它在这个场景里有几点天然契合：

- **快照和版本是原生能力**。每次提交产生一个不可变快照，支持时间回溯，和"数据集版本不可变"的思路一致。数据集版本甚至可以直接对应一个表快照或标签。
- **规模上限高**。`version_clip` 这类表到数十亿行时，MySQL 的分库分表成本很高，湖表加列式存储和分区裁剪更合适。
- **分析友好**。统计标签分布、场景覆盖度、跨版本对比、血缘影响分析，用 SQL 引擎批量跑比在线库轻松，也不会影响在线业务。
- **与数据本体同源**。元数据和 clip 都在 OSS，权限、生命周期、跨地域复制可以统一管理。
- **模式演进方便**。clip 增加新字段（比如新传感器、新标签维度）不用做大表 DDL。

#### 它不擅长的地方

湖表格式本质是面向批处理和分析的，不是 OLTP 数据库：

| 场景 | 湖表 | 关系库 |
|---|---|---|
| 点查、毫秒级响应 | 弱，通常秒级 | 强 |
| 频繁小事务、状态流转 | 弱，提交是乐观并发，冲突要重试 | 强 |
| 高频小批量写入 | 容易产生小文件，需要持续合并 | 无此问题 |
| 大规模扫描、聚合分析 | 强 | 弱 |
| 历史快照、时间回溯 | 强（原生） | 要自己设计 |
| 运维复杂度 | 高（元数据服务、合并、过期快照清理、引擎选型） | 低（托管） |

对应到前面设计的表，适合放哪里比较清楚：

| 表 | 建议位置 | 原因 |
|---|---|---|
| `version_clip`、`clip`、`clip_tag`、`lineage_edge` | 规模大时放湖表 | 体量大、以追加和批量分析为主、很少更新 |
| `dataset`、`dataset_version`（含状态） | 关系库 | 小表，有状态机和强一致要求 |
| `task_dataset_ref` | 关系库 | 训练启动时同步写，需要低延迟和事务 |
| `protection`、`cleanup_audit` | 关系库 | 清理程序必须读到最新值，不能有延迟 |
| `version_shard`（缓存状态、最近读取时间） | 关系库 | 更新频繁，是小批量状态更新 |

训练启动校验这条链路也不需要查大表：它读的是 OSS 上的 manifest 和库里的 `dataset_version` 一行，和湖表无关。

#### 是否有必要，看这几个信号

**暂时不需要**：clip 在千万级以内、版本在几百个以内、分析需求以按版本查清单为主。此时托管 MySQL 加好分区足够，上湖只会增加运维负担。

**值得引入**：
1. `version_clip` 行数逼近十亿级，分库分表已经很痛。
2. 经常需要做跨版本、跨标签的大规模统计分析，或要和特征、训练日志等其他数据联合分析。
3. 需要对元数据本身做时间回溯（"三个月前这个版本的 clip 清单和标签是什么样"）。
4. 已经有现成的湖仓平台和团队经验，边际成本低。

**要警惕的误区**：因为"别人都在用"而整体迁移。把状态机、引用关系、保护标记这类强一致的小表放进湖表，会遇到提交冲突和读到旧数据的问题，清理类操作尤其危险（读到过期的保护状态会误删）。

#### 一个可行的演进路径

1. **起步**：全部用托管 MySQL，表设计如前述。
2. **同步导出**：把 clip、version_clip、clip_tag 定期同步一份到湖表（按日或增量），专供分析和报表使用，在线链路仍读 MySQL。
3. **规模触发后**：把这几张大表的"事实源"迁到湖表，MySQL 只保留控制面小表和状态。
4. **可选**：用湖表快照承载数据集版本，manifest 中记录快照 ID，与现有的哈希校验并存。

另外，多模态训练数据本身也有专用的数据湖格式（如 Lance 这类面向图像、点云、向量的列存格式），可以直接承载样本数据而不仅是元数据，适合训练时高吞吐随机读取。这个方向和本文的元数据话题相对独立，如果你们的样本数据读取是瓶颈，可以单独评估。

如果想继续，我可以把这个"混合方案"补进《智驾数据集元数据表设计》，标明每张表放在哪一层，并加上从 MySQL 同步到湖表的方式和迁移触发条件。

## 对话中的几个关键结论

1. "mldb"在对话中按"元数据库方案"理解，推荐托管 MySQL / PolarDB 作为元数据事实源；该理解尚未经用户确认。
2. 数据集版本 = 清单（manifest），不复制数据本体；版本不可变，修复数据一律生成新版本。
3. 校验值分层计算（文件 → clip → shard → manifest），manifest_hash 独立存放并可签名。
4. 数据集存储方案与 SLA 提升方案关联不强，已改为独立文档。
5. 数据湖思想合理但非必须：控制面用关系库，大表在规模触发后再迁到湖表。
