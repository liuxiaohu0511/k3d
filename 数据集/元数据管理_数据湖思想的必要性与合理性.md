# 元数据管理：数据湖思想的必要性与合理性

| 项目 | 内容 |
|---|---|
| 文档版本 | V0.1（草案） |
| 编制日期 | 2026-10-12 |
| 配套文档 | 《智驾数据集存储与规划方案》《智驾数据集元数据表设计》 |
| 结论摘要 | 合理，但不是必须，也不应整体替换关系库；推荐"控制面用关系库，大体量分析面用数据湖表格式"的混合方案，是否上湖取决于规模和查询模式 |

> 说明：本文的"数据湖"指 Iceberg、Delta、Hudi、Paimon 等湖仓表格式，数据落在 OSS 上，由 Spark、Flink、Trino 等引擎读写。文中规模阈值为经验值，需结合实际压测确认。

---

## 1 问题与结论

**问题**：很多平台用数据湖的思想管理元数据，我们的数据集元数据是否有必要、是否合理采用？

**结论**

1. **合理**：数据湖表格式在"快照即版本"、超大规模、分析友好等方面与数据集元数据管理契合。
2. **非必须**：规模在千万级 clip 以内时，托管 MySQL 加合理分区即可满足，上湖会增加运维负担。
3. **不宜整体替换**：状态机、引用关系、保护标记等强一致的小表不适合放进湖表，误放会带来提交冲突和读到旧数据的风险，清理类操作尤其危险。
4. **推荐混合方案**：控制面（小表、强一致、低延迟）用关系库，分析面（大表、追加为主、批量统计）用湖表，规模触发后再逐步迁移。

---

## 2 数据湖思想对元数据的价值

| 价值点 | 说明 |
|---|---|
| 快照与版本原生支持 | 每次提交产生不可变快照，支持时间回溯，与"数据集版本不可变"的思路一致；数据集版本可直接对应一个表快照或标签 |
| 规模上限高 | `version_clip` 这类表到数十亿行时，MySQL 分库分表成本很高；湖表加列式存储和分区裁剪更合适 |
| 分析友好 | 标签分布、场景覆盖度、跨版本对比、血缘影响分析，用 SQL 引擎批量跑，不影响在线业务 |
| 与数据本体同源 | 元数据与 clip 同在 OSS，权限、生命周期、跨地域复制可统一管理 |
| 模式演进方便 | clip 新增字段（新传感器、新标签维度）无需对大表做 DDL 变更 |

---

## 3 数据湖的局限

湖表格式本质面向批处理和分析，不是 OLTP 数据库。

| 场景 | 湖表 | 关系库 |
|---|---|---|
| 点查、毫秒级响应 | 弱，通常秒级 | 强 |
| 频繁小事务、状态流转 | 弱，提交为乐观并发，冲突需重试 | 强 |
| 高频小批量写入 | 易产生小文件，需持续合并 | 无此问题 |
| 大规模扫描、聚合分析 | 强 | 弱 |
| 历史快照、时间回溯 | 强（原生） | 需自行设计 |
| 运维复杂度 | 高（元数据服务、文件合并、过期快照清理、引擎选型） | 低（托管） |

---

## 4 混合方案：各表放在哪一层

对应《智驾数据集元数据表设计》中的各表：

| 表 | 建议位置 | 原因 |
|---|---|---|
| `version_clip`、`clip`、`clip_tag`、`lineage_edge` | 规模大时放湖表 | 体量大，以追加和批量分析为主，很少更新 |
| `dataset`、`dataset_version`（含状态） | 关系库 | 小表，有状态机和强一致要求 |
| `task_dataset_ref` | 关系库 | 训练启动时同步写，需要低延迟和事务 |
| `protection`、`cleanup_audit` | 关系库 | 清理程序必须读到最新值，不能有延迟 |
| `version_shard`（缓存状态、最近读取时间） | 关系库 | 更新频繁，属于小批量状态更新 |

**训练启动校验链路不依赖湖表**：它只读 OSS 上的 manifest 和关系库里 `dataset_version` 的一行记录。

## 5 判断是否引入的信号

### 5.1 暂时不需要

- clip 在千万级以内
- 版本在几百个以内
- 分析需求以"按版本查清单"为主

此时托管 MySQL 加好分区足够，上湖只增加运维负担。

### 5.2 值得引入

1. `version_clip` 行数逼近十亿级，分库分表已经困难。
2. 经常需要跨版本、跨标签的大规模统计分析，或要与特征、训练日志等其他数据联合分析。
3. 需要对元数据本身做时间回溯，例如"三个月前这个版本的 clip 清单和标签是什么样"。
4. 已有现成的湖仓平台和团队经验，边际成本低。

### 5.3 常见误区

- **因为"别人都在用"而整体迁移**：把状态机、引用关系、保护标记这类强一致小表放进湖表，会遇到提交冲突和读到旧数据的问题。
- **忽略湖表运维成本**：小文件合并、快照过期、元数据服务高可用都需要持续投入。
- **混淆元数据与数据本体**：湖表格式管理的是结构化元数据，传感器数据本体仍放 OSS，经缓存层加速训练读取。

## 6 演进路径

| 阶段 | 做法 | 触发条件 |
|---|---|---|
| 起步 | 全部使用托管 MySQL / PolarDB，按《元数据表设计》建表 | — |
| 同步导出 | 将 `clip`、`version_clip`、`clip_tag` 定期（按日或增量）同步一份到湖表，专供分析和报表；在线链路仍读 MySQL | 出现跨版本、跨标签的批量分析需求 |
| 事实源迁移 | 将上述大表的事实源迁到湖表，MySQL 仅保留控制面小表和状态 | `version_clip` 逼近十亿级，或分库分表成本明显偏高 |
| 版本对接（可选） | 用湖表快照承载数据集版本，manifest 中记录快照 ID，与现有哈希校验并存 | 需要对元数据做时间回溯 |

**迁移时的保障**

1. 双写或增量同步期间，以对账任务比对两侧行数和关键字段，确认一致后再切换读流量。
2. 切换前保留回退路径，MySQL 侧数据至少保留一个完整周期。
3. 清理、保护等强一致链路不参与首批迁移。

---

## 7 补充：样本数据本身的湖格式

多模态训练数据本身也有专用格式（如 Lance 这类面向图像、点云、向量的列存格式），可直接承载样本数据而不只是元数据，适合训练时高吞吐随机读取。该方向与元数据管理相对独立，如果样本读取是瓶颈，可单独评估，不与本文的元数据选型绑定。

---

## 8 待确认事项

1. 当前与预期的 clip 规模、版本数量，决定是否需要走到"事实源迁移"阶段。
2. 公司是否已有湖仓平台（Iceberg / Paimon 等）和维护团队，决定引入成本。
3. 分析类需求的清单与频率（跨版本对比、覆盖度统计、血缘影响分析等），决定同步导出的优先级。
4. 是否需要对元数据做时间回溯，决定是否采用湖表快照对接数据集版本。
5. 元数据查询的延迟要求（在线点查与离线分析的占比）。
