这是个很有价值的问题——K8s 和 Docker 生态里这类"写了但不代表真的会发生"的字段还真不少，是新手排错时最容易被误导的地方。按 Docker 和 K8s 分类整理。

## Docker / Dockerfile 层

### `ENV`（部分场景）
```dockerfile
ENV APP_ENV=production
```
`ENV` 本身**是**真实生效的——它会被写入镜像的环境变量。但如果应用代码/启动脚本压根没读取这个变量，它就只是"存在但没人用"的摆设。跟你之前发现的 `server.port` 场景正好相反：这次是**声明生效了，但下游没消费它**。

### `VOLUME`
```dockerfile
VOLUME /data
```
这行声明了"这个路径打算做成数据卷"，Docker 也确实会在容器启动时自动创建一个匿名卷挂载到这个路径。**但它不会自动帮你持久化数据到宿主机**，很多人以为写了 `VOLUME` 数据就自动跑到本地磁盘上了，其实还是在 Docker 管理的匿名卷里，容器删了如果没手动 `-v` 挂载，数据一样可能跟着丢（虽然卷本身不会立刻被删，但很容易变成没人管的孤儿卷）。

### `USER`
```dockerfile
USER appuser
```
这个**是真实生效的**（会真的切换运行用户），但很多人以为写了这行就等于容器"安全"了，其实如果基础镜像里 `appuser` 这个用户本身有 sudo 权限，或者应用有其他提权漏洞，这行声明起不到实际隔离作用，容易给人虚假的安全感。

### `HEALTHCHECK`
```dockerfile
HEALTHCHECK CMD curl -f http://localhost:8080/health || exit 1
```
这个在**纯 Docker（`docker run`）场景下是生效的**，会影响 `docker ps` 里的健康状态显示。但**一旦进了 K8s，这个字段会被完全忽略**——K8s 有自己的一套 `livenessProbe`/`readinessProbe`/`startupProbe`（就是你在 digital.yaml 里看到的那些），跟 Dockerfile 里的 `HEALTHCHECK` 毫无关系，是两套互不相干的机制。

## Kubernetes 层

### `terminationMessagePath` / `terminationMessagePolicy`
```yaml
terminationMessagePath: /dev/termination-log
```
声明了"容器异常退出时，把日志写到这个路径，K8s会读出来展示在events里"。但**只有应用自己主动往这个路径写内容才有意义**，绝大多数镜像根本没这个逻辑，所以这个字段在几乎所有实际场景里都是空转的摆设。

### `hostname` / `subdomain`（Pod spec）
```yaml
spec:
  hostname: my-pod
  subdomain: my-subdomain
```
这两个字段**只有在配合 headless Service 使用时才会真正生效**（生成可解析的DNS记录）。如果没有对应的 headless Service，这两个字段写了也不会产生任何可用的DNS效果，纯粹是摆设。

### `resources.requests`（在某些场景下会"失真"）
```yaml
resources:
  requests:
    cpu: "250m"
```
这个字段本身是真实生效的（影响调度），**但如果没配 `LimitRange` 或没开启对应的准入控制**，一些集群允许你把 `requests` 设置得远低于`limits`，甚至有的环境（尤其是本地k3d这种测试集群）调度器压根不严格校验资源余量，会出现"声明了requests，但实际调度时该节点资源早就超卖"的情况——申请单交了，但没人真的按这个数字来分配。

### `imagePullPolicy: IfNotPresent`（配合 `latest` tag 时会"看起来没生效"）
```yaml
image: my-app:latest
imagePullPolicy: IfNotPresent
```
这个字段本身逻辑是对的，但很多人踩坑在于：**`latest` tag 配 `IfNotPresent`，会导致你以为改了代码重新构建了镜像，重新部署后Pod却还在跑旧代码**——因为本地/节点上"已经有"一个叫 `my-app:latest` 的镜像了，K8s判断"存在就不拉新的"，根本不会检测这个 `latest` 背后的内容是不是变了。这不是字段本身"无效"，而是**语义跟大多数人的直觉不符**，是新手很容易中招的坑。

### `Service` 的 `port` 命名（`name` 字段，单端口时）
```yaml
ports:
  - name: http
    port: 80
```
如果 Service 只暴露**一个端口**，这个 `name` 字段其实**可写可不写**，不影响任何功能。只有当一个 Service 有**多个端口**时，`name` 才从"摆设"变成"必填项"（K8s会强制要求，不写会直接报错校验失败）。这算是"看场景决定是否生效"的典型例子。

### `Deployment` 的 `revisionHistoryLimit`
```yaml
revisionHistoryLimit: 10
```
这个字段**只影响能回滚到几个历史版本**，跟你的应用运行时行为、性能、资源占用完全无关，纯粹是"元数据管理"层面的声明，很多人误以为这个数字关系到性能或者资源限制。

## 一个通用的判断技巧

遇到不确定某个字段"是不是真的生效"，可以用这个思路快速判断：

**问自己：这个字段的值，是被谁在什么时候"读取并执行"的？**

- 如果答案是"某个具体的控制器/调度器/kubelet 在某个明确阶段会读它" → 真实生效（如 `resources.limits`、`livenessProbe`）
- 如果答案是"应用代码需要自己主动去读这个环境变量/文件才有意义" → 声明性质，取决于下游是否消费（如你发现的 `server.port`、`ENV`）
- 如果答案是"仅仅是给人看的元数据，没有任何组件会基于它做决策" → 纯文档（如 `EXPOSE`、无对应LimitStack时的部分`terminationMessagePath`）

这个思路能帮你以后遇到新字段时，不用死记硬背，自己判断它属于哪一类。
