## 1 概述

### 1.1 背景与目的

1. 当前平台 SLA 未达目标，计算模块故障对业务产生直接影响（具体数据见第 2 章）。
2. 本次专项目标：提升计算模块与全平台的可用性、稳定性，压降故障时长与故障频次。
3. 切入场景：ACK（阿里云容器服务 Kubernetes）集群五大痛点：
   - IP 地址耗尽，导致任务调度失败
   - 节点磁盘占用率高，触发节点驱逐、任务中断
   - 调度任务缺少重试机制与断点续跑能力
   - 节点 GPU 掉卡，算力被无效占用
   - 任务镜像下载带宽打满，导致任务无法启动

**现状判断**：当前计算侧线上问题较多、正向方案推进较慢，主要有三方面原因：

1. 平台历史债较多，问题定位和消解需要时间。涉及底层 infra 的问题需要与基础团队沟通解决，目前沟通效率较低，双方也尚未就 SLA 保障形成共识。
2. 问题的识别和定位不够精准，没有形成长效的解决方案。
3. 平台缺少面向业务方的任务感知信息：业务方不清楚任务需要多少 CPU、GPU 和内存，资源配置靠经验估计；任务报错后看不到直观的异常原因和分析；任务执行时长没有告警。

本方案据此强调四点：用失败根因看板精准识别问题（5.6）；与基础团队对齐 SLA 目标与协作机制；把每个高频问题的治理结果固化为长效方案（第 8 章）；补齐面向业务方的任务感知能力（5.7）。

### 1.3 优化思路

按"问题盘点 → 根因深挖 → 专项治理 → 机制固化 → 长效保障"闭环推进，先用数据说明"哪个问题丢了多少 SLA"，再据此排序治理优先级。

### 1.4 现有架构与可复用能力

平台基于 Argo Workflow（3.8.8）+ 阿里云 ACK 构建，监控与自愈已有基础，本方案优先复用，缺口再补建。

| 层级 | 现有能力 | 采集 / 覆盖内容 | 在本方案中的用途 |
|---|---|---|---|
| 编排层 | Argo Workflow | 工作流与步骤状态、重试、产物 | 统一重试、断点续跑、Pod 与产物清理 |
| 应用层 | ARMS | 负载、接口出错率、内存使用率、请求数、异常请求数（偏后端应用） | 应用级 SLA 指标，需补充任务维度指标 |
| 节点层 | node-problem-detector（DaemonSet） | 硬件与内核类故障，转为 K8s Event | 节点故障、DiskPressure 等事件源 |
| 事件层 | k8s-eventer（Deployment） | 采集 K8s Event | 统一事件告警、故障归因统计（支撑 2.2） |
| GPU 层 | ACK GPU 故障发现与自愈 | 故障发现 → 节点隔离 → 节点排水 → 自动修复 → 解除隔离 | GPU 掉卡处置；已开启但存在漏检，需增强并与 Argo 重试联动 |

**现状确认**：ACK GPU 自愈已开启，但部分 GPU 异常捕获不到，需要增强；NPD 与 k8s-eventer 的事件和指标尚需打通采集链路，并结合 GT 或 Fishcat 告警；ARMS 提供调度后端指标，不提供工作流层面指标，任务级（Pod 维度）资源指标也无法从 ARMS 获取，需与阿里 ACK 团队沟通采集方式；镜像统一从公司自建 pkg 与 Harbor 源拉取，部分镜像达 100–200GB，不使用 ACR 企业版；BI 看板由专人负责，底层为 ClickHouse，GT / Fishcat 负责告警与看板推送。

### 2.3 现象清单

1. **算力资源层**：节点 / 虚拟算力故障、资源过载与闲置冲突、扩缩容不及时、底层环境偶发异常。
2. **调度服务层**：调度失败、延迟、排队超时、算力分配不均、调度组件单点与重启抖动。
3. **任务运行层**：长任务中断、并发冲突与资源抢占、异常兜底缺失、资源配置靠经验估计、用户看不到失败原因、执行时长无告警。
4. **依赖链路层**：存储、网络、中间件、权限服务异常传导。
5. **平台共性**：告警滞后与噪音、故障定位慢、单点与容灾不足、变更引发故障占比高、容量评估不足、涉及底层 infra 的问题跨团队沟通效率低。

| 问题 | 主类 | 次要诱因 |
|---|---|---|

| 磁盘高占用 | 系统性短板（临时文件无生命周期管控） | 缺少巡检与清理流程、瞬时写满 |
| GPU 掉卡 | 突发性故障 | ACK 自愈已开启但存在漏检，且与 Argo 重试、告警未联动 |
| 无重试 / 断点续跑 | 系统性短板 | 依赖与节点抖动 |
| 镜像带宽打满 | 系统性短板（缺少分发加速） | 大规模并发拉取的瞬时冲击 |

## 3 通用根因分析

> ACK 专项根因见第 4 章各小节。

1. **技术架构**：集群冗余与容灾策略不足；核心组件缺少降级、熔断、限流；调度算法与资源分配机制存在缺陷；平台历史债较多，问题定位和消解周期长。
2. **运维体系**：巡检覆盖不全，隐性问题无法提前发现；应急预案不完善、处置链路冗长；历史故障整改不到位、问题重复复发；问题识别与定位不够精准，未形成长效解决方案。
3. **监控体系**：计算链路关键指标缺失，无全链路观测；阈值不合理，无法提前预警；日志与链路追踪不足，定位效率低；缺少任务级资源画像与面向业务方的诊断信息。
4. **流程管理**：变更评审、灰度、回滚不严格；容量评估与压测未常态化；SLA 责任划分不清、缺少量化考核；与基础团队尚未形成 SLA 保障共识。

### 4.1 IP 耗尽治理

**现象与影响**：部分节点 Pod IP 分配失败，新任务调度失败，节点无法正常注册与调度。

**根因**

- 技术：Pod 网络模型（VPC-CNI、Terway）IP 池容量规划不足，未按业务峰值预留网段。
- 运维：未监控节点 / 集群 IP 池水位，缺少耗尽前预警与扩容预案，故障多为被动发现。
- 监控：缺少 IP 使用率监控与告警。

**治理方案**

| 措施 | 完成标志 |
|---|---|
| 通过 VPC OpenAPI 定时采集 Pod 交换机（vSwitch）剩余可用 IP 数，并采集节点 Pod 数与 ENI 上限，分级告警（建议 70% 预警 / 80% 严重 / 90% 紧急） | 告警覆盖全部集群 |
| 按业务峰值评估，新增 Pod 交换机并规划足够网段（建议掩码不大于 /19，至少 8192 个 IP） | 网段扩容完成、水位回落 |
| 启用 IP 池动态扩容与回收 | 配置上线并验证 |
| 制定 IP 耗尽应急预案 | 预案评审并演练 |

**选型**：行业通行做法是在 Terway 下新增 Pod 交换机扩容 IP（网络插件创建后不可更换）。新交换机需与原交换机同可用区；只有新建 ENI 才使用新交换机，存量节点已有 ENI 不变，需扩容节点或滚动替换。多交换机时，可将选择策略由默认 ordered 改为 random，或按节点池绑定交换机，避免突发扩容把 IP 集中耗尽在同一个交换机。

**验收指标**：IP 池使用率峰值 ≤ 80%；IP 耗尽导致的调度失败 ≤ N 次 / 季度。

### 4.2 磁盘高占用治理

**现象与影响**：节点触发 DiskPressure 被标记为 NotReady，运行中 Pod 被强制驱逐，正在执行的任务中断失败。

**根因**

- 技术：任务运行中生成大量超大临时文件，无自动清理、限额约束，持续堆积；叠加镜像与容器日志冗余（缺少镜像 GC、日志轮转）。
- 运维：未制定临时文件专项管控与定期清理机制，未常态化巡检磁盘占用。
- 监控：缺少磁盘分级预警阈值。

**治理方案**

| 措施 | 完成标志 |
|---|---|
| 在 Argo 模板中为任务容器配置 ephemeral-storage requests / limits，限制单任务临时文件 | 限额在全部工作流模板生效 |
| 配置 Argo podGC 与 ttlStrategy，工作流结束后自动清理 Pod 与记录；产物清理启用 artifactGC（当前 Argo 3.8.8 已支持） | 残留 Pod 与产物抽检为零 |
| 镜像 GC、容器日志轮转、冗余文件定期清理 | 定时任务运行正常 |
| 基于 NPD / k8s-eventer 的 DiskPressure 事件与节点磁盘指标设置多级告警（建议 70% / 80% / 85%），数据盘支持自动扩容 | 告警覆盖率 100% |
| 优化 Pod 驱逐优先级（PriorityClass），优先保障核心任务 | 驱逐策略评审并灰度上线 |

**选型**：临时存储限额 vs 外挂独立存储 / 扩大数据盘，对比成本与隔离效果。

**验收指标**：磁盘告警覆盖率 100%；磁盘压力导致的节点驱逐 ≤ N 次 / 月。

### 4.3 GPU 掉卡治理

**现象与影响**：GPU 设备失效，相关任务报错或卡死，算力被虚占，任务成功率下降。

**根因**

- 技术：驱动异常、硬件故障或显存泄漏导致 GPU 失效；ACK GPU 自愈已开启，但部分 GPU 异常捕获不到，漏检时任务仍会卡死或失败；被排水的任务能否由 Argo 自动重跑尚未保证。
- 运维：漏检的异常类型缺少复盘与清单；驱动版本缺少统一基线。
- 监控：NPD / k8s-eventer 的事件与指标尚未采集回来，未形成分阶段告警与 SLA 归因统计。

**治理方案**

| 措施 | 完成标志 |
|---|---|
| 复盘 GPU 自愈漏检的异常类型，补充检测项（如 DCGM / nvidia-smi 检查或 NPD 自定义规则）并接入 ACK 自愈流程 | 漏检场景清单完成，增强上线 |
| 打通 NPD、k8s-eventer 的事件与指标采集链路，对掉卡、隔离、排水、修复各阶段结合 GT / Fishcat 告警 | 四个阶段事件均有告警 |
| 自愈四步骤（隔离 → 排水 → 自动修复 → 解除隔离）的耗时与结果纳入指标 | 隔离时效、修复时长可统计 |
| Argo 工作流配置 retryStrategy，被排水的步骤自动调度到健康节点重跑 | 掉卡演练中任务自动恢复 |
| 统一驱动版本管理与变更流程 | 版本基线发布 |

**选型**：在已开启的 ACK GPU 自愈基础上做功能增强（推荐）vs 自研独立巡检；重点评估新增检测项的误报率、自愈排水对运行中任务的影响与触发阈值。

**验收指标**：掉卡发现到隔离时效 ≤ N 分钟；掉卡导致的批量任务失败事故 ≤ N 次 / 季度。

### 4.4 任务重试与断点续跑

**现象与影响**：节点异常、GPU 掉卡、依赖抖动等偶发异常直接导致任务失败；长任务中断后只能从头执行，重复计算浪费算力。

**根因**：Argo 工作流模板未统一配置 retryStrategy，步骤级 CheckPoint 与幂等设计缺失，调度链路容错能力弱；无退避与去重策略，重试可能瞬间打爆调度与资源。

**治理方案**

| 措施 | 完成标志 |
|---|---|
| 在 Argo 公共模板统一配置 retryStrategy：limit（建议 3 次）、backoff（duration、factor、maxDuration）实现指数退避 | 策略写入公共模板并生效 |
| 区分可重试（节点 / 资源 / 网络抖动）与不可重试（代码 / 参数错误）失败，用 retryPolicy 与 expression 按退出码判定 | 失败分类规则发布 |
| 重试时避开上次失败的节点（affinity 排除） | 重试落点验证通过 |
| 幂等设计与去重规范 | 规范评审通过 |
| 断点续跑：长任务拆成多个步骤，中间结果落产物 / 外部存储，失败重试时复用已成功步骤；任务内部通过 CheckPoint 恢复 | 长任务分批接入 |
| 限制单任务最大资源占用与最长运行时间（activeDeadlineSeconds），异常任务自动清理 | 资源与超时上限策略生效 |

**选型**：Argo 模板层统一配置（推荐，侵入低）vs 业务侧自实现；断点续跑按任务类型选择“步骤拆分 + 产物复用”或“任务内 CheckPoint”，评估对业务代码的侵入程度。

**验收指标**：重试成功率 ≥ X%；长任务断点续跑覆盖率分阶段达到 100%。

### 4.5 镜像下载带宽治理

**现象与影响**：大规模任务并发拉取镜像（部分镜像达 100–200GB）时带宽打满，镜像下载超时或失败，任务无法启动；同批任务集中重试进一步放大带宽压力，形成恶性循环。

**根因**：镜像统一从公司自建 pkg 与 Harbor 源拉取（集中式分发），缺少 P2P 分发、镜像预热、本地缓存，镜像过大且并发拉取时带宽不可控（本质为基础设施 / 镜像分发层问题）；监控上缺少镜像拉取的带宽、失败率与链路追踪。

**治理方案**

| 措施 | 完成标志 |
|---|---|
| 自建 Dragonfly P2P 分发：Harbor 原生支持对接 Dragonfly 的 P2P 预热（Harbor 2.12 及以上对应 Dragonfly 2.1.59 及以上）；节点部署 Dragonfly 客户端并配置 containerd 镜像代理，节点之间互相分发，减轻 Harbor 出口带宽压力 | 核心集群灰度上线 |
| 高频镜像通过 Harbor 预热策略（手动、定时或事件触发）预热到 P2P 引擎；镜像瘦身（复用基础层，模型与数据文件移出镜像改为外部存储挂载）；评估 Nydus 等按需加载方案 | 高频镜像预热覆盖 |
| 配置拉取限速与并发控制：kubelet 镜像并发拉取参数，以及 Argo parallelism 与 synchronization 信号量，限制同时启动的大镜像任务数 | 参数上线 |
| 镜像拉取失败任务退避重试，避免集中重试 | 策略生效 |
| 补充镜像拉取带宽、失败率监控与告警 | 告警上线 |

**镜像瘦身与大文件外移**

对 100–200GB 的镜像，拆分比任何分发优化都直接：把模型、数据等大文件从镜像移到共享存储，镜像只留运行环境与代码，体量可从百 GB 降到几 GB，也能让 P2P 与预热更有效。注意这是把压力从镜像仓库转移到存储，需要压测验证。

1. **先盘点**：对最大的 10 个镜像做分层分析，确认大头装的是什么【待确认：模型 / 数据，还是依赖环境】。

| 内容 | 处理方式 |
|---|---|
| 模型权重、数据集、字典文件 | 外移到共享存储 |
| 依赖包（CUDA、框架、Python 包） | 保留在镜像，作为基础层复用 |
| 业务代码 | 保留，与镜像版本绑定 |
| 构建缓存、中间产物 | 直接删除 |

2. **存储选型**（具体规格、吞吐上限需与 ACK、存储团队确认【待确认】）：

| 方式 | 适合场景 | 注意点 |
|---|---|---|
| NAS | 通用文件读取、中小规模并发 | 并发读大文件时吞吐容易成为瓶颈 |
| CPFS | 高吞吐、大规模并发读取 | 成本较高，需确认节点网络支持 |
| OSS 挂载 | 数据量大、读多写少、成本敏感 | 不适合小文件和随机读，不宜当本地盘用 |
| 存储 + 数据缓存加速（如 Fluid） | 多任务反复读同一批数据 | 数据缓存到节点，降低对后端的重复读取，但需引入额外组件 |

3. **Argo 改造方式**（改造量从低到高，建议从第一种开始，按压测结果再升级）：
    - 直接挂载：在工作流模板声明 PVC 或存储卷，任务读挂载路径，业务代码基本只需改路径。
    - 启动前预取：用 initContainer 或前置步骤把数据拷到节点本地盘，再让主任务读本地，适合反复读取、需避开共享存储随机读的场景。
    - 数据缓存层：集群部署缓存组件，多个任务共享节点缓存，适合高并发且数据集稳定的场景，但新增运维对象。

4. **新增风险与应对**：

| 风险 | 应对 |
|---|---|
| 并发压力转移：大量任务同时读同一份数据，存储带宽被打满 | 错峰启动，用 Argo parallelism 与信号量限制并发，必要时加缓存层 |
| 版本与一致性：数据被覆盖或误删，同一版本任务表现不一致 | 数据目录加版本号，约定只增不改 |
| 启动路径变长：现象从“镜像拉不下来”变成“卡在加载数据” | 5.6 根因分类的“依赖”类下增加二级分类“数据加载超时” |
| 权限与隔离：多业务共用存储，可能误写 | 目录隔离，只读挂载 |
| 跨可用区：存储与节点不同可用区，延迟与带宽变差 | 存储与计算节点尽量同可用区 |

5. **推进步骤**：盘点最大镜像 → 选一个最大、最常用的镜像试点，对比拉取耗时、启动耗时、存储带宽峰值 → 模拟并发启动压测，确认存储不成为新瓶颈 → 制定镜像规范（单镜像体积上限、必须外移的内容），在构建流水线加入体积检查。

**选型**：不使用 ACR 企业版，ACK 官方 P2P 加速与按需加载不可用。候选：① Dragonfly 自建 P2P（Harbor 原生支持对接，当前 Harbor 版本是否匹配【待确认】，pkg 源的拉取能否同样走 Dragonfly 代理【待确认】；100–200GB 的镜像还需评估 P2P 节点的磁盘与缓存容量），解决并发拉取；② 节点预热 + 镜像瘦身与大文件外移（见上），减少单个镜像体量（100–200GB 的镜像优先做这一项）；③ Nydus 等按需加载，需镜像转换，改造成本较高。三者对比运维复杂度与收益，Argo 模板同步配置退避重试，避免集中重试。

**验收指标**：镜像拉取失败率 ≤ X%；带宽打满导致的任务启动失败 ≤ N 次 / 季度。

### 5.6 失败根因分类与统计看板

任务调度量大，失败占比很小时总成功率始终很高，不能反映治理效果。改为对每个失败任务归因，按根因统计失败数与失败率，用看板暴露高频原因。

**根因分类（两级，可按实际数据调整）**

| 一级分类 | 二级示例 | 判定依据 |
|---|---|---|
| 网络 / IP | Pod 无可用 IP（ContainerCreating） | Pod 事件、Terway 日志 |
| 节点 / 存储 | 磁盘压力驱逐、节点 NotReady、OOM | NPD / k8s-eventer 事件 |
| GPU | 掉卡、驱动异常、显存不足 | NPD、GPU 自愈事件 |
| 镜像 | 拉取超时、ErrImagePull、ImagePullBackOff | Pod 事件 |
| 调度 | 排队超时、资源不足、调度后端异常 | 调度后端指标（ARMS） |
| 依赖 | 存储、网络、中间件、权限服务异常 | 步骤日志与依赖监控 |
| 业务 | 代码或参数错误、业务超时 | 退出码、步骤日志 |
| 未分类 | 无法判定 | 目标逐步压降 |

判定顺序：先按 Pod 与节点事件匹配（置信度高），再按 Argo 步骤失败信息与退出码，仍无法判定的归入“未分类”。Pod 通过 Argo 自带的 workflows.argoproj.io/workflow 标签关联到任务。

**统计口径**

| 指标 | 口径 |
|---|---|
| 根因失败任务数 | 首次失败归属该根因的任务数，含重试后成功的任务（避免重试掩盖问题） |
| 根因失败率 | 根因失败任务数 / 提交任务数，用万分比（‱）表示 |
| 根因占比 | 根因失败任务数 / 失败任务总数 |
| 最终失败率 | 重试后仍失败的任务数 / 提交任务数 |
| 重试挽回率 | 重试后成功的任务数 / 首次失败任务数 |
| 影响卡时 | 失败任务及重试消耗的卡时，反映算力损失 |

**看板视图**

1. Top N 根因帕累托图：累计占比达到 80% 的前几类根因，作为下一阶段治理对象，并回填 2.2 的损失测算与第 4 章优先级。
2. 按周趋势：各根因失败率走势，验证治理措施是否见效。
3. 下钻：按集群、节点池、业务、镜像、模板拆分，并能跳转到失败任务清单。
4. 未分类占比：作为归因质量指标。

**实现路径**：Argo 任务失败时打上根因标签（如通过退出钩子）→ 与 NPD / k8s-eventer 事件按 Pod 与任务关联 → 汇总写入 ClickHouse（公司 BI 的底层存储）→ 由负责 BI 的同事在 BI 工具中建看板；GT / Fishcat 负责阈值告警与看板推送。分工上，分类规则与明细表由平台侧负责，看板由 BI 负责人建设。

**ClickHouse 失败任务明细表（建议字段）**

| 字段 | 说明 |
|---|---|
| 任务 ID、工作流名称、模板 | 关联 Argo 任务 |
| 提交时间、开始时间、结束时间 | 计算调度延迟、运行时长 |
| 集群、节点池、节点 | 下钻维度 |
| 业务、镜像 | 下钻维度 |
| 首次失败根因（一级、二级） | 看板核心维度 |
| 判定依据 | 事件 / 退出码 / 日志，便于复核归因 |
| 重试次数、最终状态 | 计算最终失败率、重试挽回率 |
| 影响卡时 | 失败与重试消耗的卡时 |

### 5.7 任务感知能力建设（面向业务方）

平台目前缺少面向业务方的任务感知信息：资源配置靠经验估计，失败原因看不到，执行时长无告警。下面三项能力补齐这块，并与 5.6 共用同一套数据链路（ClickHouse），让业务方自助发现并处理问题。

**5.7.1 任务资源画像与配置推荐**

现象：业务方不清楚任务需要多少 CPU、GPU 和内存，资源靠经验估计；申请偏小会 OOM 或被驱逐，偏大则造成算力闲置。

| 措施 | 完成标志 |
|---|---|
| 采集每个任务运行期间的 CPU、内存、GPU 利用率与显存使用，记录峰值与分位值 | 指标采集覆盖全部工作流 |
| 按任务类型 / 模板汇总，绘制资源使用曲线，对比申请值与实际使用值 | 任务维度曲线可查看 |
| 基于历史数据推荐 requests / limits（如取 P95 或 P99 峰值加安全余量，比例经压测确认） | 推荐接口或页面上线 |
| 提交任务时展示推荐值，业务方可一键采纳 | 业务方可自助调整 |

数据来源与采集方式：任务级资源指标无法从 ARMS 获取，需与阿里 ACK 团队沟通，确认能否采集到 Pod 层面的指标。可行路径如下，均需 ACK 团队确认：

- CPU、内存：ACK 集群 Prometheus 监控（ack-arms-prometheus）采集的容器指标，粒度到 Pod。
- GPU：ACK GPU 监控（GPU exporter，兼容 DCGM exporter 指标），自带 Pod 维度看板。节点驱动需 418.87.01 及以上，Profiling 指标需 450.80.02 及以上；GPU 共享场景的自定义指标会计费。
- 关联任务：Pod 带有 Argo 工作流标签，可按标签把 Pod 指标聚合到任务，再写入 ClickHouse。

与 ACK 团队待确认【待确认】：

1. 各集群是否已开启 Prometheus 监控与 GPU 监控。
2. Pod 维度指标的采集间隔与保留时长；短任务是否会漏掉峰值。
3. 已结束 Pod 的历史指标能否按任务时间范围查询。
4. 指标导出到 ClickHouse 的方式（如 remote write 或 API 拉取）。
5. 采集与存储的费用。

指标：资源申请与实际使用的偏差率；因资源不足（OOM、驱逐）失败的任务占比下降；推荐值采纳率。

**5.7.2 用户侧任务诊断（报错原因可视）**

现象：任务报错后，业务方只能看到失败，看不到直观的异常原因和分析。

| 措施 | 完成标志 |
|---|---|
| 对接阿里云 SLS 任务日志与 k8s event 事件（k8s-eventer），按任务 ID 关联 | 任务维度日志与事件可统一查询 |
| 建立异常规则库：把日志关键字、退出码、事件原因映射为标准异常类型与处理建议，与 5.6 根因分类共用 | 规则库发布，覆盖高频根因 |
| 任务详情页展示失败根因、判定依据、关键日志片段与处理建议，并区分平台问题与业务问题 | 业务方可直接看到原因 |
| 无法判定的异常归入“未分类”，定期复盘补充规则 | 未分类占比逐步下降 |

指标：失败任务根因展示覆盖率；未分类占比。

**5.7.3 执行时长基线与超时告警**

现象：用户对任务执行时长没有告警，任务卡住或明显变慢时无法及时发现，超时时间也靠经验配置。

| 措施 | 完成标志 |
|---|---|
| 采集同类型任务（按模板、业务、输入规模区分）的历史执行时长，计算 P50、P95、P99 | 时长基线表建成 |
| 基于基线推荐超时时间（如 P99 加余量），在 Argo 中用 activeDeadlineSeconds 配置 | 提交任务时展示推荐值 |
| 接近或超过基线的超时与异常变慢告警，经 GT / Fishcat 通知任务负责人 | 告警到人 |
| 任务登记负责人信息 | 负责人字段覆盖率 100% |

指标：已配置超时的任务占比；超时告警送达负责人的比例；卡住任务的平均发现时长。

## 8 长效机制

1. SLA 日监控、周复盘、月总结，数据周报 / 月报。
2. 故障闭环管理：上报 → 定位 → 整改 → 复盘 → 固化；每个高频根因沉淀为长效方案（规则、工具或平台能力），避免重复定位。
3. 明确各模块 SLA 责任人和考核指标；季度专项稳定性复盘。
4. 建立技术迭代优化台账，持续整改存量短板；与基础团队就 SLA 保障达成共识，明确 infra 类问题的责任人、响应时限与升级路径。
5. 持续引入新技术、新架构；团队稳定性能力培训与技能沉淀。
